# ADR-002: Módulo version_manager com subprocess git

## Status

Aceito

## Data

2026-06-07

## Contexto

O MVP exige comparar o repositório local com o remoto e retornar commits ahead para exibição no modal. O projeto já usa `subprocess` extensivamente (`gpu_manager`, `process_manager`) e não possui dependências git em Python. A verificação ocorre via endpoint autenticado chamado uma vez por sessão de navegação.

Decisões de esclarecimento técnico:
- Branch de referência: branch atual do checkout local vs. `origin/<mesmo-branch>`
- Sem limite de commits retornados
- Sem cache server-side (cada request executa fetch + comparação)
- Frontend persiste dismiss em `sessionStorage`

## Decisão

Implementar a lógica git em um novo módulo `version_manager.py` na raiz do projeto, usando **apenas `subprocess`** para invocar o binário `git` nativo:

- `git rev-parse` para validar work-tree, obter branch atual e SHAs local/remoto
- `git fetch --quiet origin <branch>` com timeout configurável antes da comparação
- `git log HEAD..origin/<branch>` com `--format` estruturado para extrair SHA, mensagem, autor e data

Expor um endpoint autenticado `GET /api/system/version-check` em `llama_manager.py` que delega a `version_manager.check_for_updates(install_root)`.

Respostas tipadas via modelos Pydantic em `schemas.py` (`VersionCommit`, `VersionCheckResponse`).

## Alternativas Consideradas

### Alternativa 1: GitPython

- **Descrição**: Usar a biblioteca `GitPython` para operações tipadas no repositório.
- **Prós**: API Python idiomática; menos parsing de stdout.
- **Contras**: Nova dependência pip; camada extra de abstração; inconsistência com o padrão subprocess do projeto.
- **Por que rejeitada**: YAGNI — subprocess cobre o escopo com zero dependências adicionais.

### Alternativa 2: Lógica inline em llama_manager.py

- **Descrição**: Implementar comandos git diretamente na rota FastAPI, como `_execute_update()` faz hoje com `os.system`.
- **Prós**: Menos arquivos.
- **Contras**: Dificulta testes unitários; viola separação já estabelecida por módulos extraídos (`gpu_manager`, `process_manager`, etc.).
- **Por que rejeitada**: Testabilidade e consistência arquitetural favorecem módulo dedicado.

### Alternativa 3: Cache em memória com TTL

- **Descrição**: Cachear resultado do fetch por 5 minutos no processo FastAPI.
- **Prós**: Reduz carga em múltiplas abas/usuários simultâneos.
- **Contras**: Resultado potencialmente defasado; complexidade de invalidação; frontend já limita a 1 chamada por sessão.
- **Por que rejeitada**: Volume de chamadas no MVP é baixo; simplicidade preferida.

## Consequências

### Positivas

- Módulo isolado e testável com mocks de `subprocess.run`
- Sem novas dependências no `requirements`/venv
- Endpoint REST alinhado ao namespace `/api/system/*` existente

### Negativas

- Parsing manual de stdout do `git log --format`
- `git fetch` em cada request pode adicionar latência de rede (mitigado por timeout e chamada única no frontend)
- Comportamento depende de `git` estar no PATH e de credenciais SSH/HTTPS configuradas no servidor

### Riscos

- **Fetch lento ou bloqueante**: timeout de 30s no subprocess; falha retorna `status: error` sem modal no frontend
- **Divergência branch local/remoto**: usar branch do checkout local garante coerência com o que `git pull` do botão ATUALIZAR aplicaria
- **Work-tree sujo**: commits ahead ainda são detectados corretamente; mudanças locais não commitadas não afetam a comparação de refs

## Notas de Implementação

- `install_root` obtido de `paths.INSTALL_ROOT`
- Ordem cronológica dos commits: do mais antigo ao mais recente (ordem natural do `git log` reverso) ou explicitamente `--reverse` para cronológica ascendente conforme PRD
- Ambientes não-git: retornar `status: unavailable`, `update_available: false` — frontend não exibe modal

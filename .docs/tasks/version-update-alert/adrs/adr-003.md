# ADR-003: Frontend version.js com modal e sessionStorage

## Status

Aceito

## Data

2026-06-07

## Contexto

O PRD (ADR-001) define modal automático na abertura do dashboard, dispensável por sessão de navegação. O frontend usa módulos ESM em `static/js/` carregados via `index.js`, com padrão de overlay fixo já estabelecido pelo `login-overlay` em `_build_html()`.

## Decisão

Criar `static/js/version.js` responsável por:

1. Chamar `GET /api/system/version-check` via `apiFetch` **uma única vez** por carregamento de página (flag `checked` em memória do módulo).
2. Invocar a verificação ao final de `initDashboard()` (tanto no load autenticado quanto pós-login).
3. Renderizar/abrir o modal `#version-update-modal` (markup embutido em `_build_html()`) quando `update_available === true`.
4. Persistir dismiss em `sessionStorage` com chave `version-update-dismissed=1`; ao dispensar, ocultar modal e não reabrir na mesma sessão de navegação.
5. Suportar fechamento por botão, tecla Esc e clique no backdrop.

Exportar `checkForUpdates()` e `dismissVersionModal()`; registrar em `index.js` no objeto `window` e incluir `version.js` na lista de cache-bust de `_dashboard_js_version()`.

## Alternativas Consideradas

### Alternativa 1: Variável em memória para dismiss

- **Descrição**: Flag JS volátil sem `sessionStorage`.
- **Prós**: Implementação mínima.
- **Contras**: Reload da página (F5) reabre o modal na mesma aba — comportamento indesejado para admin em operação.
- **Por que rejeitada**: `sessionStorage` alinha melhor com "sessão de navegação" incluindo reloads.

### Alternativa 2: Modal criado dinamicamente via JS

- **Descrição**: Construir DOM do modal inteiramente em JavaScript.
- **Prós**: HTML de `llama_manager.py` mais enxuto.
- **Contras**: Inconsistente com padrão do projeto (markup no `_build_html()`); dificulta testes de contrato HTML.
- **Por que rejeitada**: Markup estático no template segue convenção existente do login-overlay.

### Alternativa 3: Polling periódico

- **Descrição**: Re-verificar a cada N minutos com `setInterval`.
- **Prós**: Detecta updates durante sessão longa.
- **Contras**: Fora do escopo do PRD MVP; aumenta chamadas ao backend.
- **Por que rejeitada**: PRD define verificação única na abertura.

## Consequências

### Positivas

- Módulo JS isolado com testes Jest dedicados (`version.test.js`)
- Reutiliza `apiFetch` para tratamento de 401
- Modal estático permite estilização Tailwind consistente com o dashboard

### Negativas

- `_build_html()` cresce com markup do modal
- `index.js` ganha mais um import/export no objeto global

### Riscos

- **Race com initDashboard**: verificação deve ser assíncrona e não bloquear polling de métricas — usar `checkForUpdates()` fire-and-forget após init
- **Modal sobre login**: só executar quando `#dashboard` visível e autenticado

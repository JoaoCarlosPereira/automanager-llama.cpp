# ADR-002: Estrutura modular dos arquivos JavaScript

> **Idioma:** escreva todo o conteúdo deste arquivo em **português brasileiro (PT-BR)**.

## Status

Aceito

## Data

2026-06-02

## Contexto

O JavaScript embutido no HTML (`llama_manager.py`, linhas 969-2074) contém aproximadamente 1100 linhas de código com funções miscelâneas agrupadas apenas por comentários genéricos (`// -- Authentication --`, `// -- Dashboard functions --`). Para facilitar testes unitários e manutenção, é necessário organizar o código em módulos coerentes.

## Decisão

Dividir o JavaScript extraído em 5 módulos separados na pasta `static/js/`:

- `auth.js` — Funções de autenticação: `handleLogin`, `handleLogout`, `changePassword`, `handleSessionExpired`, `apiFetch` (helper de sessão)
- `models.js` — Gerenciamento de modelos: `startModel`, `stopModel`, `renameModel`, `deleteModel`, `setDefaultModel`, `selectModel`, `applyModelConfig`, `getModelButtonsHtml`, `downloadModel`, `updateDownloads`
- `metrics.js` — Métricas e monitoramento: `updateMetrics`, `updateStatus`, `updateUptime`, `startLogs`, `stopDashboardPolling`, `startDashboardPolling`, `ensureStatusPolling`
- `gpu.js` — GPU e auto-balance: `getContextSize`, `setContextSize`, `tokensToContextK`, `syncContextSizeCustomVisibility`, `onContextSizePresetChange`, `onContextSizeCustomInput`, `updateTotal`, `balanceWeights`, `redistributeUnpinnedWeights`, `onGpuPinToggle`, `bindGpuManualListeners`, `applyGpuWeightsToUI`, `markManualGpuChange`, `cancelAutoBalance`, `hideAutoBalanceCapacityAlert`, `showAutoBalanceCapacityAlert`, `modelIncapableBadgeHtml`, `modelIncapableRowClass`, `isModelHardwareIncapable`, `updateAutoBalanceProfileBadge`, `resetToDefaults`
- `index.js` — Arquivo principal de inicialização: `initDashboard`, configuração do `fixedIp`, event listeners de DOM, e import/ordem de execução dos módulos

Cada módulo será carregado como `<script type="module">` via `import` no HTML, mantendo a compatibilidade com navegadores modernos.

## Alternativas Consideradas

### Alternativa 1: Arquivo único `app.js`

- **Descrição**: Manter tudo em um único arquivo extraído
- **Prós**: Simplicidade, menos configuração de import
- **Contras**: Dificuldade de testar funções isoladamente, arquivo muito grande (~1100 linhas), sem separação de responsabilidades
- **Por que rejeitada**: Não facilita a organização dos testes unitários conforme o PRD exige cobertura modular

### Alternativa 2: Estrutura de classes (ES6)

- **Descrição**: Reescrever as funções como métodos de classes (ex: `AuthService`, `ModelManager`)
- **Prós**: Alta coesão, fácil de mockar, padrão moderno
- **Contras**: Refatoração significativa, risco de introduzir bugs, mudança de paradigma (de funções para classes), dependência de `this` e instância
- **Por que rejeitada**: Overhead desnecessário para um projeto que não usa framework frontend. Manter funções puras é suficiente e menos propenso a erros na migração

### Alternativa 3: Modularização com exports individuais (Escolhida)

- **Descrição**: Extrair para módulos com `export function` mantendo a lógica de funções puras
- **Prós**: Boa separação, fácil testar cada módulo, sem mudança de paradigma, baixo risco de breakage
- **Contras**: Requer configuração de module no HTML, cada módulo precisa ser carregado na ordem correta
- **Por que escolhida**: Equilibra organização sem introduzir complexidade desnecessária. Funções puras são facilmente testáveis com Jest

## Consequências

### Positivas

- Cada módulo tem responsabilidade clara e tamanho gerenciável (~150-350 linhas)
- Testes Jest podem importar módulos específicos sem carregar toda a aplicação
- Desenvolvedores encontram funções no arquivo correto mais facilmente
- Git blame e code review ficam mais focados

### Negativas

- Necessidade de usar `type="module"` nos scripts HTML
- Variáveis compartilhadas no escopo global (`window.modelConfigs`, `statusPollTimer`, etc.) precisam ser tratadas com cuidado
- A ordem de carregamento dos módulos importa (index.js deve ser carregado por último)

### Riscos

- **Risco**: Variáveis globais como `statusPollTimer`, `metricsTimer` não são exportadas mas são acessadas por múltiplos módulos
  **Mitigação**: Declarar variáveis de estado no `index.js` e passar como parâmetro quando necessário, ou manter como propriedades de `window` para compatibilidade com código existente
- **Risco**: `alert()` e `confirm()` usados extensivamente são difíceis de testar
  **Mitigação**: Criar wrappers `showAlert(msg)` e `showConfirm(msg)` que podem ser mockados nos testes

## Notas de Implementação

1. Adicionar `type="module"` em cada `<script>` do HTML
2. Usar `import` no `index.js` para importar os outros módulos na ordem:
   ```html
   <script type="module" src="/static/js/auth.js"></script>
   <script type="module" src="/static/js/models.js"></script>
   <script type="module" src="/static/js/metrics.js"></script>
   <script type="module" src="/static/js/gpu.js"></script>
   <script type="module" src="/static/js/index.js"></script>
   ```
3. No `index.js`, declarar variáveis de estado compartilhadas:
   ```javascript
   export let statusPollTimer = null;
   export let metricsTimer = null;
   // ... etc
   ```
4. Criar wrappers para funções de navegador:
   ```javascript
   export function showAlert(msg) { alert(msg); }
   export function showConfirm(msg) { return confirm(msg); }
   ```
5. Manter compatibilidade com `window.modelConfigs` como objeto de estado compartilhado

# ADR-004: Configuração Jest e Playwright para testes de UI

> **Idioma:** escreva todo o conteúdo deste arquivo em **português brasileiro (PT-BR)**.

## Status

Aceito

## Data

2026-06-02

## Contexto

O projeto usa Python como linguagem principal dos testes (pytest + httpx TestClient). A camada de UI adiciona JavaScript (testado com Jest) e interações de navegador (testadas com Playwright). É necessário definir configurações que integrem esses dois ecossistemas no mesmo repositório sem conflito de dependências.

## Decisão

### Jest (Unit Tests)

- Usar Jest via Node.js (npm) como runtime — o JavaScript extraído roda no ambiente JSDOM
- Configuração em `jest.config.js` na raiz do projeto:
  - `testEnvironment: 'jsdom'` para simular DOM
  - `moduleFileExtensions: ['js']`
  - `testMatch: ['**/*.test.js']`
  - `coverageDirectory: 'coverage/js'`
  - `coverageThreshold: { global: { statements: 90, branches: 90, functions: 90, lines: 90 } }`
  - `transform: {}` — sem Babel, usar ES modules nativos com `type: "module"` no `package.json`
- `package.json` na raiz do projeto com `"type": "module"` e `"jest": { ... }` inline

### Playwright (E2E Tests)

- Usar Playwright via npm (`@playwright/test`)
- Configuração em `playwright.config.ts` na raiz do projeto
- Projetos: apenas `chromium` (conforme decisão do usuário)
- `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`
- `webServer` configurado para iniciar o servidor mock FastAPI
- Testes em `tests/e2e/` com extensão `.spec.ts`

### Scripts pytest para rodar Jest

Criar `tests/e2e/conftest.py` com fixture que roda `npm test` como subprocesso, ou usar `pytest` para rodar Jest via `subprocess.run()`. Alternativamente, manter Jest e pytest como suites independentes executadas separadamente:

```bash
pytest                    # Tests Python
npm test                  # Jest unit tests (JS)
npx playwright test       # Playwright E2E tests
```

## Alternativas Consideradas

### Alternativa 1: Jest via npm + Playwright via npm (Escolhida)

- **Descrição**: Manter Jest e Playwright como dependências npm separadas do ecossistema Python
- **Prós**: Isolamento total entre ecossistemas, ferramentas otimizadas para seus propósitos, sem conflito de dependências
- **Contras**: Requer Node.js instalado, duas toolchains para gerenciar (npm + pip), dois conjuntos de scripts de teste
- **Por que escolhida**: Jest não roda em Python, Playwright Python não oferece testes unitários de JS. A divisão natural é Jest para unit + Playwright para E2E

### Alternativa 2: pytest-playwright (somente Python)

- **Descrição**: Usar `pytest-playwright` para tudo em Python, sem Jest
- **Prós**: Uma única toolchain (pytest), sem Node.js
- **Contras**: `pytest-playwright` é para E2E, não tem suporte nativo a unit tests de JS, JSDOM não é acessível via pytest
- **Por que rejeitada**: Não cobre o requisito de testes unitários de funções JavaScript isoladas

### Alternativa 3: Vitest (alternativa ao Jest)

- **Descrição**: Usar Vitest ao invés de Jest para unit tests
- **Prós**: Mais rápido que Jest, nativamente ES modules, integração com Vite
- **Contras**: Menos maduro que Jest, ecossistema de plugins menor, curva de aprendizado para novos contribuidores
- **Por que rejeitada**: Jest é o padrão da indústria com mais maturidade e documentação. Vitest seria overkill para um projeto sem build pipeline

## Consequências

### Positivas

- Testes unitários Jest são ultra-rápidos (JSDOM, sem navegador)
- Playwright cobre interações reais em navegador Chromium
- Cada suite pode ser rodada isoladamente (`npm test`, `pytest`, `npx playwright test`)
- Threshold de 90% de cobertura mantém qualidade sem ser impraticável

### Negativas

- Requer instalação de Node.js adicional no ambiente de desenvolvimento
- Duas configurações de teste para manter (jest.config.js + playwright.config.ts)
- package.json na raiz pode ser confuso para desenvolvedores Python

### Riscos

- **Risco**: Desenvolvedores Python não têm Node.js instalado
  **Mitigação**: Documentar instalação no README.md, incluir Node.js como requisito de dev
- **Risco**: Threshold de 90% pode ser difícil de atingir para funções pequenas que acessam DOM diretamente
  **Mitigação**: Ajustar threshold por arquivo se necessário, focar em cobertura de lógica de negócio

## Notas de Implementação

1. Criar `package.json` na raiz com `"type": "module"`
2. Rodar `npm install --save-dev jest jest-environment-jsdom @playwright/test`
3. Criar `jest.config.js` apontando para `static/js/*.test.js`
4. Criar `playwright.config.ts` configurando Chromium + webServer mock
5. Criar `tests/e2e/mock_server.py` com servidor FastAPI mock
6. Adicionar `node_modules/` ao `.gitignore`
7. Documentar comandos de teste no README.md

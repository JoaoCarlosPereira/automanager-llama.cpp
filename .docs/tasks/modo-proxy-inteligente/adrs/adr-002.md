# ADR-002: Tag [AGENT:...] apenas como chave de afinidade, sem regras fixas tag→backend

## Status

Aceito

## Data

2026-07-07

## Contexto

A especificação inicial previa uma tabela configurável de regras de roteamento por tag (ex.: `sql-reviewer → qwen-aux-p100-1`), permitindo ao administrador fixar o backend preferido de cada subagente. Durante o brainstorming, avaliou-se o custo/benefício dessa configuração: ela adiciona uma superfície de configuração e de UI considerável, exige manutenção manual conforme agentes e instâncias mudam, e o mesmo resultado prático (subagentes distribuídos entre GPUs, cada um preso ao seu backend) é obtido pela combinação de afinidade sticky + seleção automática least-busy.

## Decisão

Não haverá mapeamento configurável tag→backend. A tag `[AGENT:...]` (e demais fontes de identidade: headers, metadata, hash estável) serve **exclusivamente como chave de afinidade** da sessão. A escolha do backend é sempre automática: conversa principal (`[AGENT:main]` ou sem tag) prefere o backend principal; subagentes vão para o backend elegível menos ocupado. Uma vez atribuído, o backend permanece fixo pela afinidade sticky.

## Alternativas Consideradas

### Alternativa 1: Regras tag→backend editáveis pela UI

- **Descrição**: Seção do painel para criar/editar regras de backend preferido por tag, persistidas no `automanager_config.json`.
- **Prós**: Controle determinístico total; administrador garante que agente X sempre usa GPU Y.
- **Contras**: Mais UI, mais configuração para manter sincronizada com instâncias que sobem/descem; regras apontando para backends offline criam casos de erro; benefício marginal sobre o least-busy com sticky.
- **Por que rejeitada**: YAGNI — o resultado desejado (distribuição estável de subagentes entre GPUs) já emerge do sticky + least-busy sem custo de configuração.

### Alternativa 2: Regras apenas em arquivo de configuração

- **Descrição**: Mesmo mapeamento, mas editado manualmente no JSON/YAML, com UI somente leitura.
- **Prós**: Menos UI que a alternativa 1.
- **Contras**: Mesmos problemas de manutenção e casos de erro, com pior descoberta (configuração escondida).
- **Por que rejeitada**: Mesma razão da alternativa 1, com experiência pior.

## Consequências

### Positivas

- Zero configuração para o administrador: ligar o modo proxy é suficiente.
- Sem estados de erro do tipo "regra aponta para backend inexistente/offline".
- Escopo de UI e de persistência menor.

### Negativas

- O administrador não consegue forçar um subagente específico para uma GPU específica (ex.: garantir que `sql-reviewer` sempre use a P100 #1). A distribuição é ótima em carga, não em preferência manual.

### Riscos

- Se surgir demanda real por fixação manual (ex.: modelo secundário especializado para um agente), a funcionalidade pode ser adicionada em versão futura sem quebra — a tag já é extraída e registrada na sessão. Mitigação: registrar a tag detectada na tabela sticky e nos logs desde já.

## Notas de Implementação

O extrator de identidade (headers → metadata → tag → hash estável) permanece integralmente; apenas a etapa "consultar tabela de regras" deixa de existir no fluxo de decisão.

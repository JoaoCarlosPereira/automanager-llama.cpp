# ADR-001: Seleção de backend por least-busy interno com afinidade sticky

## Status

Aceito

## Data

2026-07-07

## Contexto

O Modo Proxy Inteligente precisa decidir, para cada **nova** sessão/subagente, qual instância de llama-server (backend) atenderá a conversa. Sessões existentes nunca trocam de backend (afinidade sticky obrigatória para preservar KV cache, cache de prompt e slots do llama.cpp). Todo o tráfego OpenAI-compatible já passa pelo manager (catch-all `/v1` em `llama_manager.py`), o que permite ao próprio manager observar a carga que ele mesmo encaminha. Pesquisa de mercado (LiteLLM, vLLM Router, llm-d, Paddler, TrueFoundry) confirma que balanceadores cegos (round-robin) quebram prefix caching e que afinidade de sessão com fallback least-busy é o padrão dominante.

## Decisão

Para novas sessões, o proxy escolhe o backend **menos ocupado** entre os elegíveis, contando internamente as requisições em andamento que o próprio manager encaminhou a cada backend. A escolha respeita: (1) preferência do backend principal para a conversa principal (`[AGENT:main]`, ausência de tag); (2) capacidade de contexto do backend versus tamanho estimado da requisição; (3) limite de concorrência configurável por backend (`max_parallel_requests`). Uma vez escolhido, o backend fica fixado na tabela de afinidade sticky até expirar por TTL, cair, ser desabilitado ou sofrer reassignment administrativo.

## Alternativas Consideradas

### Alternativa 1: Hash consistente da affinity_key

- **Descrição**: Mapear deterministicamente cada `affinity_key` a um backend via hash consistente, sem estado de carga.
- **Prós**: Zero estado, distribuição estável, implementação trivial, sobrevive a restart sem persistência.
- **Contras**: Cego à ocupação real — dois subagentes podem colidir na mesma GPU enquanto outra fica ociosa; não respeita limites de concorrência nem capacidade de contexto.
- **Por que rejeitada**: Com poucas GPUs (2–3 backends), colisões de hash desperdiçam hardware justamente no cenário-alvo (subagentes paralelos do Cursor).

### Alternativa 2: Slot-aware via endpoint `/slots` do llama.cpp

- **Descrição**: Consultar o endpoint `/slots` de cada llama-server em tempo real para conhecer slots livres e cache de prompt antes de cada decisão (estilo Paddler).
- **Prós**: Visão mais precisa da carga, inclusive de tráfego externo ao manager; potencial de roteamento cache-aware.
- **Contras**: Exige flag extra por instância, adiciona uma rodada de health-check por decisão de roteamento, sensível a mudanças da API do llama.cpp entre versões.
- **Por que rejeitada**: Complexidade e fragilidade desproporcionais — como todo o tráfego de inferência passa pelo manager, o contador interno é suficientemente preciso.

## Consequências

### Positivas

- Distribuição eficiente de subagentes paralelos entre GPUs heterogêneas sem dependências externas.
- Nenhuma exigência adicional na linha de comando do llama-server.
- Decisão de roteamento em memória, sem latência extra de health-check por requisição.

### Negativas

- Tráfego enviado diretamente às portas dos backends (fora do manager) não é contabilizado na carga.
- Contadores em memória zeram em restart do manager (mitigado pela persistência da tabela sticky em disco).

### Riscos

- Estimativa de tokens do prompt é aproximada; requisições no limite do contexto de um secundário podem ser roteadas de forma subótima. Mitigação: margem de segurança na verificação de contexto e fallback para o principal.

## Notas de Implementação

Contadores de requisições em andamento por porta no manager (incremento no encaminhamento, decremento na conclusão/aborto do stream). Elegibilidade avaliada sobre `get_status()["instances"]` cruzada com flags de participação no proxy.

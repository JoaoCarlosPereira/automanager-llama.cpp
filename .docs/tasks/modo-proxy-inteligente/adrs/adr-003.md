# ADR-003: Proxy inteligente assume o /v1 existente do manager (porta 8000), expondo somente o modelo principal

## Status

Aceito

## Data

2026-07-07

## Contexto

O manager FastAPI já expõe uma API OpenAI-compatible em `/v1` na porta 8000 (catch-all que roteia pelo campo `model` para a instância correspondente, com streaming SSE). A especificação exemplificava o Cursor apontando para uma porta dedicada (`:4000`). Era preciso decidir: (a) onde o proxy atende; (b) o que o `GET /v1/models` retorna com o modo ligado; (c) o que acontece com requisições que pedem um modelo secundário pelo nome real.

## Decisão

1. O Modo Proxy Inteligente **assume o `/v1` já existente na porta 8000** — nenhuma porta nova. Com o modo desligado, o `/v1` mantém o comportamento atual (roteamento direto por modelo).
2. Com o modo ligado, o `GET /v1/models` retorna **somente o modelo principal**.
3. Requisições que pedem um modelo secundário **pelo nome real continuam sendo atendidas diretamente** por aquela instância, sem sticky e sem reescrita — o roteamento inteligente só atua quando o modelo solicitado é o principal.

## Alternativas Consideradas

### Alternativa 1: Porta dedicada configurável (ex.: 4000)

- **Descrição**: Listener próprio para o proxy, separado do painel/API de gestão.
- **Prós**: Separação de tráfego de inferência e de gestão; possibilidade de firewall distinto.
- **Contras**: Porta extra para expor, configurar e documentar; clientes já apontados para a 8000 precisariam migrar.
- **Por que rejeitada**: O `/v1` da 8000 já é o ponto de entrada OpenAI-compatible da aplicação; reaproveitá-lo dá adoção imediata sem mudança de infraestrutura.

### Alternativa 2: `/v1/models` listando todos os modelos (principal primeiro)

- **Descrição**: Manter a agregação atual, apenas ordenando com o principal no topo.
- **Prós**: Secundários continuam descobríveis por dropdown.
- **Contras**: Polui o seletor de modelos do Cursor; usuário pode selecionar um secundário por engano, contornando o proxy.
- **Por que rejeitada**: O objetivo do produto é o cliente enxergar um único modelo; acesso direto a secundários permanece possível pelo nome real (sem descoberta).

### Alternativa 3: Rejeitar requisições para modelos secundários com o modo ligado

- **Descrição**: Somente o modelo principal seria aceito; demais nomes retornariam erro 404.
- **Prós**: Ocultação total dos secundários.
- **Contras**: Quebra clientes/integracões que acessavam instâncias individualmente; impede uso das instâncias excluídas do proxy.
- **Por que rejeitada**: Instâncias marcadas como "fora do proxy" precisam continuar endereçáveis individualmente.

## Consequências

### Positivas

- Zero mudança de configuração para clientes existentes; ligar o modo muda apenas o comportamento de roteamento.
- Cursor configura um único modelo e nunca vê os secundários.
- Instâncias fora do proxy permanecem plenamente utilizáveis pelo nome real.

### Negativas

- Tráfego de inferência e painel compartilham a mesma porta/processo (sem isolamento de rede entre gestão e inferência).
- Secundários ficam "ocultos mas acessíveis" — não é um mecanismo de segurança, apenas de conveniência.

### Riscos

- Clientes que hoje dependem da listagem agregada do `/v1/models` deixarão de ver os secundários com o modo ligado. Mitigação: comportamento só muda quando o administrador ativa o modo explicitamente; desligar restaura a agregação atual.

## Notas de Implementação

O ponto de decisão fica no catch-all `/v1/{path}` existente (`llama_manager.py:616-698`) e no agregador `_aggregate_models_response` (`llama_manager.py:585-613`), condicionados à flag global do modo proxy.

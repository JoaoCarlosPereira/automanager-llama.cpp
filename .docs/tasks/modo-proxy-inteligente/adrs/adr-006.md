# ADR-006: Reescrita do campo `model` por linha SSE com buffer incremental; modelo real exposto em header `x-automanager-backend`

## Status

Aceito

## Data

2026-07-07

## Contexto

O PRD (F4, F8) exige que toda resposta ao cliente — inclusive cada evento de streaming — apresente o `model` do modelo principal, mesmo quando atendida por um secundário, sem materializar a resposta em memória. O encaminhamento atual repassa **chunks brutos de bytes** (`async for chunk in response.aiter_bytes()`, `llama_manager.py:670-677`); um evento SSE (`data: {json}\n\n`) pode ser cortado no meio entre dois chunks, o que impede substituição por regex direta no chunk. A pesquisa de mercado registrou como prática comum reescrever o `model` para o alias e expor o modelo real em canal auxiliar para telemetria (LiteLLM issues #22709/#21665).

## Decisão

1. **Streaming (backend secundário)**: o gerador de encaminhamento mantém um **buffer incremental de bytes** e emite ao cliente somente linhas completas (delimitadas por `\n`). Linhas `data: {...}` com JSON válido contendo `"model"` têm o campo substituído pelo nome do modelo principal e são re-serializadas; qualquer outra linha (`data: [DONE]`, comentários keep-alive `:`, linhas vazias, JSON inválido) passa intocada. O resto do fluxo permanece streaming puro — nada além da linha corrente é retido.
2. **Não-streaming (backend secundário)**: parse do JSON de resposta, substituição de `model`, re-serialização. Em corpo não-JSON, repasse intocado.
3. **Requisição encaminhada**: o body é re-serializado com `model` trocado pelo nome interno do backend escolhido; demais campos (conhecidos e desconhecidos) preservados. Tags `[AGENT:...]` não são removidas.
4. **Atalho de fidelidade**: quando o backend escolhido é o próprio principal, nenhuma reescrita ocorre — repasse de chunks brutos como hoje.
5. **Telemetria**: toda resposta roteada pelo proxy inclui os headers `x-automanager-backend: <porta>` e `x-automanager-backend-model: <modelo interno>` (resolve a pergunta em aberto do PRD; headers não afetam clientes OpenAI-compatible).

## Alternativas Consideradas

### Alternativa 1: Substituição por regex/replace direto em cada chunk bruto

- **Prós**: Mínima mudança no gerador atual.
- **Contras**: O nome do modelo pode ser cortado entre dois chunks TCP; corromperia JSON silenciosamente e de forma intermitente.
- **Por que rejeitada**: Incorreção intermitente é o pior tipo de bug para clientes de streaming.

### Alternativa 2: Agregar a resposta inteira e reescrever no final

- **Prós**: Reescrita trivial.
- **Contras**: Viola requisito explícito do PRD (streaming ponta a ponta, TTFT preservado).
- **Por que rejeitada**: Requisito obrigatório do produto.

### Alternativa 3: Não reescrever eventos SSE (só respostas não-stream)

- **Prós**: Zero overhead no streaming.
- **Contras**: Cursor exibiria/registraria nome de modelo diferente do configurado em cada chunk, quebrando a transparência exigida.
- **Por que rejeitada**: Contradiz o requisito central "o cliente sempre vê o modelo principal".

## Consequências

### Positivas

- Reescrita correta independentemente de onde o TCP corta os eventos.
- Overhead limitado a decode/encode de linhas apenas quando o backend é secundário.
- Modelo/backend reais permanecem observáveis via headers para depuração e telemetria.

### Negativas

- Latência marginal por linha em respostas de secundários (parse JSON por evento SSE); irrelevante frente ao tempo de geração de tokens.

### Riscos

- Formatos SSE inesperados de versões futuras do llama-server. Mitigação: qualquer linha que não seja `data: {json válido}` passa intocada (fail-open); testes unitários cobrem eventos cortados entre chunks, `[DONE]` e usage final.

## Notas de Implementação

O parse do evento final com `usage`/`timings` (quando presente) alimenta `tokens_processed` da sessão sticky, best-effort. Headers de resposta continuam filtrados por `_filter_proxy_headers` (`llama_manager.py:79-85`); `content-length` já é removido, o que acomoda corpos reescritos com tamanho diferente.

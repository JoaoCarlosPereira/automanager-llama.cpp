# ADR-003: Detecção de compatibilidade MTP via llama-server --model-info

## Status

Aceito

## Data

2026-06-07

## Contexto

O PRD (ADR-002) exige ignorar silenciosamente configurações MTP quando o modelo não suporta a feature. É necessário um critério confiável para decidir se as flags `--spec-type draft-mtp` e `--spec-draft-n-max` entram no comando de start. Modelos GGUF MTP-compatíveis expõem metadado `nextn_predict_layers > 0` (definido pelo conversor HF→GGUF para famílias Qwen3.5/3.6 e similares).

## Decisão

Implementar `gpu_manager.detect_model_mtp(model_path: str) -> bool` que executa `llama-server --model-info` (mesmo subprocess pattern de `detect_model_layers`) e retorna `True` quando o output contém `nextn_predict_layers` com valor inteiro `> 0`. Em falha de subprocess, timeout ou metadado ausente, retorna `False`.

## Alternativas Consideradas

### Alternativa 1: Heurística por nome de arquivo

- **Descrição**: Considerar compatível se path contém `MTP`, `-mtp` ou similar.
- **Prós**: Zero subprocess; instantâneo.
- **Contras**: Falsos positivos/negativos; nomes de arquivo não padronizados; não cobre modelos MTP sem sufixo no nome.
- **Por que rejeitada**: Insuficiente para política silenciosa confiável; risco de passar flags em modelos incompatíveis (assert no llama-server).

### Alternativa 2: Híbrido heurística + model-info

- **Descrição**: Atalho por nome; fallback para model-info quando toggle ligado.
- **Prós**: Menos chamadas subprocess em modelos claramente rotulados.
- **Contras**: Duas fontes de verdade; comportamento inconsistente entre modelos.
- **Por que rejeitada**: YAGNI — volume de starts não justifica otimização prematura; `detect_model_layers` já estabelece precedente de model-info.

### Alternativa 3: Sempre passar flags e deixar llama-server falhar

- **Descrição**: Ignorar detecção; confiar no runtime.
- **Prós**: Implementação mínima.
- **Contras**: Viola ADR-002; start pode falhar ou logar erros em modelos sem MTP.
- **Por que rejeitada**: Contradiz requisito de produto.

## Consequências

### Positivas

- Detecção alinhada ao metadado real do GGUF.
- Reutiliza infraestrutura existente (`CUDA_VISIBLE_DEVICES=""`, timeout 15s).
- Comportamento previsível: sem metadado = sem MTP aplicado.

### Negativas

- Subprocess adicional no start quando MTP está ligado (aceitável — já existe `detect_model_layers` no mesmo fluxo).
- Depende de versão do llama-server que emite `nextn_predict_layers` no output de `--model-info`.

### Riscos

- Formato de output do llama-server muda — mitigar com regex tolerante e testes unitários com fixtures de output.
- Modelos futuros com chave de metadado diferente — monitorar upstream llama.cpp.

## Notas de Implementação

Regex sugerida: `nextn_predict_layers\s*=\s*(\d+)` — retornar `True` se grupo > 0.

Chamada em `process_manager.start()` apenas quando `mtp_enabled=True`; cache opcional fora do MVP.

# ADR-004: Priorização GPU no Auto Balance com Limite de 70%

**Data**: 2026-06-07  
**Status**: Aceito  
**Autor**: Cy Create TechSpec  

## Contexto

O Auto Balance existente distribui pesos entre GPUs para maximizar VRAM usage sem OOM. Com a adição da CPU como dispositivo, o algoritmo precisa decidir quando e quanto usar da CPU, evitando configurações impráticas (ex: 80% da carga na CPU, resultando em performance inutilizável).

## Decisão

O Auto Balance prioriza GPUs como dispositivos de compute principal e usa a CPU apenas como último recurso, com limite máximo de 70% de peso para a CPU.

### Regras de Negócio

1. **GPU-first**: O algoritmo tenta sempre distribuir 100% entre as GPUs primeiro
2. **CPU como último recurso**: A CPU só recebe carga quando todas as GPUs já estão ativas e ainda há OOM
3. **Limite de 70%**: Auto Balance nunca atribui mais de 70% ao CPU
4. **Redistribuição**: Se o cálculo resulta em CPU > 70%, o excedente é redistribuído para as GPUs

```python
def _should_add_cpu(self, all_gpus: list, weight_map: dict) -> bool:
    """CPU só entra se todas as GPUs já estão ativas e ainda há OOM."""
    return len(all_gpus) > 0 and all(g in weight_map for g in all_gpus)

MAX_CPU_WEIGHT = 70  # Constante global
```

### Fluxo do Algoritmo

```
AutoBalanceProber.discover()
├── Fase 1: _find_feasible_split()
│   ├── Para cada count (1..n_gpus):
│   │   └── Tenta distribuir entre GPUs, probe llama-server
│   └── Todas as GPUs ativas + OOM?
│       └── Adiciona CPU: weight = min(70%, 100 - sum(gpu_weights))
│
└── Fase 2: _maximize_vram_per_gpu()
    ├── Para cada GPU: binary search max weight
    └── Recalcula CPU = 100 - sum(gpu_weights)
        └── Se CPU > 70%: limita a 70%, redistribui para GPUs
```

## Alternativas Consideradas

### Abordagem 1: GPU-First com Limite 70% (Escolhida)

Prioriza GPUs, limita CPU, redistribui excedente.

**Vantagens:**
- Garante que GPUs são sempre usadas primeiro (performance ótima)
- Limite de 70% evita configurações impráticas
- Comportamento previsível para o usuário
- Alinha com a mentalidade de que GPU >> CPU para inferência

**Desvantagens:**
- Se VRAM das GPUs é 80% do necessário, CPU fica limitada a 70% mesmo que o modelo caia
- Redistribuição pode ser conservadora

### Abordagem 2: CPU como Parceira Igual

Auto Balance distribui entre GPUs e CPU sem priorização.

**Vantagens:**
- Maior flexibilidade para distribuir carga
- Pode encontrar soluções onde GPU-only falha

**Desvantagens:**
- Pode atribuir 80-90% para CPU (performance inutilizável)
- Resultado imprevisível para o usuário
- Viola o princípio de que GPU é o dispositivo de compute primário

### Abordagem 3: GPU-First Sem Limite

Prioriza GPUs mas não limita CPU.

**Vantagens:**
- Mais flexível que Abordagem 1
- Cabe modelos maiores

**Desvantanes:**
- Pode resultar em CPU > 70% (performance ruim)
- Usuário pode não entender por que Auto Balance escolheu configuração lenta
- Sem proteção contra configurações impráticas

## Consequências

- GPU sempre aparece primeiro no spill order (comportamento existente preservado)
- CPU é adicionada ao final do processo, após esgotar GPUs
- Limite de 70% é uma proteção prática: 70% de CPU é aceitável para modelos grandes, > 70% degrada demais
- Se modelo ainda não cabe com CPU a 70%: erro "Modelo além da capacidade"
- Usuário pode sobrescrever manualmente (peso > 70%) via UI — o limite é apenas do Auto Balance
- OOM Watchdog continua funcionando: reduz GPU weight, recalcula CPU weight automaticamente

# ADR-002: Extensão do Schema GPUWeight com Campo Device

**Data**: 2026-06-07  
**Status**: Aceito  
**Autor**: Cy Create TechSpec  

## Contexto

O Automanager usa o schema `GPUWeight` (schemas.py) para representar pesos de dispositivos na distribuição de carga. Atualmente, todos os dispositivos são GPUs com `index >= 0`. A CPU offload exige representar um dispositivo não-GPU no mesmo schema, mantendo compatibilidade com requests existentes.

## Decisão

Extender o modelo `GPUWeight` com um campo string `device` com valor padrão `"gpu"`. A CPU usa `device="cpu"` e `index=-1` como convenção para não conflitar com índices de GPU.

```python
class GPUWeight(BaseModel):
    index: int
    weight: float
    name: str
    active: bool = True
    is_main: bool = False
    pinned: bool = False
    device: str = "gpu"  # "gpu" | "cpu"
```

### Regras de Negócio

- Dispositivos GPU: `device="gpu"`, `index >= 0`, `is_main` pode ser `True` ou `False`
- Dispositivo CPU: `device="cpu"`, `index=-1`, `is_main` sempre `False`
- Campo é backward-compatible: valor padrão `"gpu"` garante compatibilidade com requests antigos
- Leitura de configs antigas usa `.get("device", "gpu")` para fallback seguro

## Alternativas Consideradas

### Abordagem 1: Extensão do GPUWeight (Escolhida)

Adiciona campo `device` ao schema existente.

**Vantagens:**
- Minimiza mudanças (1 campo adicionado)
- Mantém a mesma estrutura de dados para UI e APIs
- `gpu_weights` na config JSON já suporta CPU naturalmente
- Auto Balance e process_manager trabalham com uma lista unificada
- backward-compatible com default

**Desvantagens:**
- Semânticamente `GPUWeight` não descreve CPU

### Abordagem 2: Schema Separado CPUWeight

Cria `CPUWeight` separado e lista unificada `List[Union[GPUWeight, CPUWeight]]`.

**Vantagens:**
- Separação semântica clara entre GPU e CPU
- Cada schema tem campos específicos ao seu tipo

**Desvantagens:**
- Mudança significativa em schemas, UI, APIs
- Auto Balance precisaria de polimorfismo complexo
- Config JSON precisaria de discriminação de tipo
- Mais código, mais superfície de bug

### Abordagem 3: Índice Negativo para CPU

Usa `index=-1` como convenção implícita para CPU, sem campo extra.

**Vantagens:**
- Mínima mudança (apenas convenção de índice)
- Sem mudança no schema

**Desvantagens:**
- Não é explicitamente documentado no schema
- Validação de peso máximo da CPU (70%) não tem indicador óbvio
- Código futuro pode assumir que todos os índices são GPUs
- Menos robusto a mudanças

## Consequências

- O campo `device` é explícito, auto-documentado e validável
- Configs antigos funcionam sem modificação (default `"gpu"`)
- Auto Balance verifica `device == "cpu"` para aplicar regras específicas (priorização, limite 70%)
- UI usa `device` para esconder radio button da CPU
- `is_main` é sempre `False` para `device="cpu"` (validação no frontend e backend)

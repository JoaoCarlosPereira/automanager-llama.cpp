# ADR-003: Cálculo Dinâmico de --n-gpu-layers

**Data**: 2026-06-07  
**Status**: Aceito  
**Autor**: Cy Create TechSpec  

## Contexto

O `process_manager.py` hardcoded `-ngl 99` ao iniciar o llama-server, enviando todas as camadas do modelo para a GPU. Com CPU offload, o valor de `--n-gpu-layers` deve ser calculado dinamicamente com base no peso total das GPUs ativas.

## Decisão

Implementar `compute_n_gpu_layers()` em `process_manager.py` que calcula o número de camadas para GPU baseado na soma dos pesos das GPUs ativas:

```python
def compute_n_gpu_layers(gpu_weights: List[GPUWeight], total_model_layers: int) -> int:
    gpu_weight_sum = sum(w.weight for w in gpu_weights if w.device == "gpu")
    gpu_ratio = gpu_weight_sum / 100.0
    return max(0, round(total_model_layers * gpu_ratio))
```

### Detalhes de Implementação

- `total_model_layers` é inferido como 999 (valor padrão do llama-server para modelos desconhecidos)
- O llama-server clampa internamente `--n-gpu-layers` ao número real de camadas do modelo
- Se GPU weight soma 100%: todas as camadas na GPU
- Se GPU weight soma 0%: todas as camadas na CPU (`--n-gpu-layers 0`)
- `--tensor-split` continua GPU-only (CPU não participa de tensor split)

## Alternativas Consideradas

### Abordagem 1: Cálculo Proporcional (Escolhida)

Peso GPU → fração de camadas na GPU, peso CPU → fração de camadas na CPU.

**Vantagens:**
- Simples, direto, previsível
- Alinha com a UX de controle de peso do usuário
- Funciona com qualquer modelo (independente de tamanho)
- llama-server lida com o clamping internamente

**Desvantagens:**
- Não considera que camadas iniciais/finais têm peso diferente no consumo de VRAM
- Proporção linear pode não ser otimizada para todos os modelos

### Abordagem 2: Consulta ao llama-server

Consultar o llama-server pelo número real de camadas do modelo antes de iniciar.

**Vantagens:**
- Número exato de camadas do modelo
- Precisão máxima no cálculo

**Desvantagens:**
- Requer iniciar um probe ou parser do modelo antes de decidir camadas
- Adiciona latência ao fluxo de início
- Complica o fluxo do Auto Balance (que já faz probes)

### Abordagem 3: Mapa de Camadas Fixo

Manter um mapeamento pré-calculado de modelos conhecidos para suas camadas.

**Vantagens:**
- Preciso para modelos conhecidos

**Desvantagens:**
- Não escala para modelos novos
- Requer manutenção de banco de dados de modelos
- Complica a arquitetura sem benefício real (llama-server clampa internamente)

## Consequências

- Substituição do hardcoded `-ngl 99` por cálculo dinâmico
- CPU offload funciona automaticamente quando GPU weight < 100%
- OOM Watchdog recalcula pesos e, por consequência, `--n-gpu-layers`
- Auto Balance considera VRAM usada como proxy para verificar se o cálculo está correto
- Se modelo tem menos de 999 camadas, o llama-server ignora o excesso silenciosamente

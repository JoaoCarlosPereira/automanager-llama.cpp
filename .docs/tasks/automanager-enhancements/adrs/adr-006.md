# ADR-006: Status OFFLINE — Dual Verification Approach

**Date:** 2026-05-19  
**Status:** Accepted  
**Context:** The dashboard can display stale "ONLINE" or active status states when no model process is running. This occurs when the manager page is loaded after a process stop, or when the browser cache serves a stale state. We need to guarantee that OFFLINE is the correct initial state.  
**Decision:** Implement dual verification on page load: (1) `GET /status` returns the authoritative running state from `psutil.process_iter()` on the server side. (2) Client-side JS independently verifies by attempting a `fetch('/status')` and checking the `running` field. If the server is unreachable (manager restarted but process still running), the client shows a WARNING state. The initial state before any API call is OFFLINE (neutral slate, no glow).  
**Alternatives Considered:**
- **Trust /status only:** Simplest approach but no client-side safety net if the manager is in a transitional state.
- **Triple verification with timeout:** Adds a loading state and 5-second timeout. More complex state machine, diminishing returns for a cosmetic fix.
**Consequences:**
- Initial state is always OFFLINE (clear, unambiguous)
- Server-side verification via `/status` is authoritative
- Client-side verification catches edge cases (manager restarting, network blips)
- No additional API endpoints needed
- Minimal JS changes: add initial state logic and dual-verification flow
- Warning state for unreachable server prevents silent failures

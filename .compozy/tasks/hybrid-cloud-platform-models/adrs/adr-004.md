# ADR-004: Shared Sidecar Lifecycle and Real Model Discovery

## Status

Accepted

## Date

2026-07-09

## Context

Codex, Claude Code, and Google Antigravity all route through CLIProxyAPI. Starting one process per platform would duplicate listeners, health checks, generated config, and provider registry state. CLIProxyAPI also maintains a model registry that powers `/v1/models` and includes provider-oriented model metadata.

The user selected the MVP behavior where AutoManager preserves model IDs returned by the sidecar instead of inventing synthetic names or provider prefixes.

## Decision

AutoManager will run one shared CLIProxyAPI sidecar for all MVP platform integrations. Starting any detected platform integration ensures the shared sidecar is running, then marks that platform backend active in AutoManager's runtime state.

For model discovery, AutoManager will query the sidecar's `/v1/models` endpoint and forward the returned model records through AutoManager's `/v1/models` aggregation. The MVP will preserve the model IDs returned by CLIProxyAPI. AutoManager may add metadata for UI display when it can do so without changing the model `id`.

Smart proxy routing will continue to forward to a local port. For platform backends, that port is the shared sidecar port, and eligibility is controlled by the platform `backend_id`.

## Alternatives Considered

### Alternative 1: One Sidecar Process Per Platform

- **Description**: Start a separate CLIProxyAPI process for Codex, Claude Code, and Google Antigravity.
- **Pros**: Easier mental model for one card equals one process.
- **Cons**: More ports, more process supervision, duplicated config, and higher chance of inconsistent model registry state.
- **Why rejected**: A single sidecar matches CLIProxyAPI's design and reduces MVP operational surface.

### Alternative 2: Expose Synthetic Platform Models

- **Description**: Return one AutoManager-owned model per platform, such as `codex` or `claude-code`.
- **Pros**: Simple UI and no dependency on upstream model names.
- **Cons**: Hides actual model availability and forces AutoManager to translate synthetic IDs back to provider models.
- **Why rejected**: The selected behavior is to preserve real model IDs returned by CLIProxyAPI.

### Alternative 3: Prefix All Platform Models

- **Description**: Rewrite sidecar model IDs to names such as `platform/codex/<model>`.
- **Pros**: Avoids collisions and makes provider origin obvious.
- **Cons**: Changes client-visible model IDs and requires reverse mapping for every request.
- **Why rejected**: It violates the selected MVP behavior of preserving sidecar IDs.

## Consequences

### Positive

- One process is easier to supervise and health-check.
- API clients see the real model IDs exposed by CLIProxyAPI.
- The existing AutoManager proxy can keep routing to local HTTP ports.

### Negative

- Provider-level activation is tracked by AutoManager, while model-level details come from the shared sidecar.
- Duplicate model IDs across local and cloud backends still need deterministic aggregation behavior.
- Provider filtering depends on metadata available from CLIProxyAPI model records or sidecar registry behavior.

### Risks

- If the sidecar exposes models for providers the operator did not start, AutoManager could show more cloud models than intended. Mitigation: track active platform backends in AutoManager and filter sidecar models by provider metadata when available; otherwise document the sidecar as the source of model availability for the MVP.

## Implementation Notes

Represent each active platform backend as a lightweight runtime instance that points to the shared sidecar port. Keep one process record for sidecar supervision and separate platform status records for cards and proxy eligibility.

# ADR-005: Startup-Only Platform Detection with Persisted Preferences

## Status

Accepted

## Date

2026-07-09

## Context

The PRD requires automatic detection of Codex, Claude Code, and Google Antigravity. Detection can be performed continuously during every model scan, periodically with a cache, or once during AutoManager startup. The user selected startup-only detection for the MVP.

AutoManager also needs to persist operator preferences such as proxy eligibility and display settings without persisting stale installation state as durable truth.

## Decision

AutoManager will detect supported platform integrations once during server startup. The result will live in memory for the AutoManager process lifetime and will be included in model catalog/status responses. Installing or removing a platform tool while AutoManager is running will require restarting AutoManager to refresh detection in the MVP.

AutoManager will persist only operator preferences keyed by `backend_id`, such as `proxy_eligible`, optional display settings, and last selected primary backend. It will not persist detection results as authoritative availability state.

## Alternatives Considered

### Alternative 1: Detect on Every Model Scan with a Short Cache

- **Description**: Re-run platform detection whenever `/models` is scanned, using a short TTL to reduce overhead.
- **Pros**: Reflects installs/removals without restarting AutoManager.
- **Cons**: Adds scan-time process/path checks and can make the local model catalog less deterministic.
- **Why rejected**: The selected MVP behavior is startup-only detection.

### Alternative 2: Persist Detection Results Until Manual Refresh

- **Description**: Save detected tools in config and update them through a manual rescan action.
- **Pros**: Stable UI and explicit refresh.
- **Cons**: Persists stale environment data and adds another operator action to the MVP.
- **Why rejected**: Detection should be automatic at startup and preferences should be the only durable platform data.

## Consequences

### Positive

- Startup detection is simple, predictable, and easy to test.
- The catalog avoids repeated environment probes during normal scans.
- Preferences survive restarts without treating stale detection as truth.

### Negative

- New installations are not visible until AutoManager restarts.
- Removed tools may remain visible until the next restart unless runtime start/health checks mark them not-ready.

### Risks

- Operators may expect immediate detection after installing a tool. Mitigation: show a concise not-ready reason and document that MVP detection refreshes on restart.

## Implementation Notes

Create a platform detector invoked during FastAPI application startup or module initialization. The detector should check `PATH` and known install locations for each MVP tool, record executable path or missing reason, and expose the result through a platform catalog service.

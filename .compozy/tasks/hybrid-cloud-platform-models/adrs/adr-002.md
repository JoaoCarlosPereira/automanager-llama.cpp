# ADR-002: CLIProxyAPI HTTP Sidecar for Platform Backends

## Status

Accepted

## Date

2026-07-09

## Context

AutoManager is a Python/FastAPI application that discovers local `.gguf` models, starts `llama-server` processes, tracks running instances by local port, and forwards OpenAI-compatible `/v1` requests to those ports. The hybrid platform feature must add Codex, Claude Code, and Google Antigravity without reworking the local model flow.

CLIProxyAPI already implements the provider-specific authentication, translation, routing, and `/v1/models` behavior for the requested cloud subscription tools. It can run as a local HTTP server and can use the authentication state already present on the machine.

## Decision

AutoManager will integrate platform backends by starting and supervising CLIProxyAPI as a local HTTP sidecar process. The sidecar will bind to `127.0.0.1` on an AutoManager-managed port, use a generated runtime config under AutoManager's data directory, and be forwarded through AutoManager's existing `/v1` proxy surface.

AutoManager will not implement provider login flows, provider API-key screens, or provider-specific request translators in the MVP. It will rely on the CLIProxyAPI sidecar and the user's existing local provider authentication.

## Alternatives Considered

### Alternative 1: Embed CLIProxyAPI SDK Through a Go Helper

- **Description**: Build a dedicated Go helper binary using the CLIProxyAPI SDK and ship it as part of AutoManager.
- **Pros**: Stronger control over process shape, config loading, and health endpoints.
- **Cons**: Adds build, packaging, and version compatibility work before the MVP validates the integration.
- **Why rejected**: The existing CLIProxyAPI HTTP server already fits AutoManager's port-based backend model.

### Alternative 2: Reimplement Platform Adapters in Python

- **Description**: Implement Codex, Claude Code, and Google Antigravity adapters directly inside AutoManager.
- **Pros**: Single runtime and no sidecar process.
- **Cons**: Duplicates provider-specific auth, translation, token refresh, model registry, and failure handling already implemented by CLIProxyAPI.
- **Why rejected**: It increases MVP scope and creates long-term provider maintenance risk.

## Consequences

### Positive

- Reuses CLIProxyAPI's provider support instead of duplicating it.
- Fits AutoManager's current HTTP-backend forwarding model.
- Keeps local model behavior unchanged.
- Keeps provider credentials outside AutoManager.

### Negative

- AutoManager must supervise one additional process.
- Runtime failures can originate from the sidecar or from a provider behind the sidecar.
- Packaging must account for how the CLIProxyAPI executable is found on the server.

### Risks

- CLIProxyAPI command-line flags or config schema may change. Mitigation: isolate command construction in one sidecar manager and add tests around the generated config.
- The sidecar may be unavailable or unhealthy. Mitigation: health-check the local port and surface concise not-ready reasons in the UI.

## Implementation Notes

Add a small platform sidecar manager that owns executable detection, port allocation, generated config path, process start/stop, health checks, and `/v1/models` discovery. Keep its public contract close to the existing process status shape so the existing proxy code can consume it with minimal branching.

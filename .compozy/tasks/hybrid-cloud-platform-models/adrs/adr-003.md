# ADR-003: Stable Backend Identity for Platform Integrations

## Status

Accepted

## Date

2026-07-09

## Context

AutoManager currently keys most model settings by normalized `model_path`. This works for local files, but platform integrations are not filesystem paths. Reusing path normalization for cloud tools would create fragile pseudo-paths and could accidentally feed non-file identifiers through path-specific migration logic.

The hybrid feature needs stable identifiers for cards, persisted operator preferences, smart proxy eligibility, primary backend selection, and runtime status.

## Decision

AutoManager will introduce explicit backend identity fields for hybrid backends:

- `backend_id`: stable logical identifier, such as `platform:codex`, `platform:claude-code`, or `platform:google-antigravity`.
- `backend_type`: `local` or `platform`.
- `provider`: provider key for platform integrations, such as `codex`, `claude`, or `antigravity`.

Local models will continue to use normalized `model_path` as their durable key. Platform preferences will be persisted under a platform-specific config map keyed by `backend_id`, not under `model_configs` and not through `normalize_model_path`.

Compatibility fields such as `model_path` may remain in runtime responses while existing UI and proxy code are migrated, but platform IDs must not be treated as real files.

## Alternatives Considered

### Alternative 1: Use Pseudo-Paths Like `cloud://codex`

- **Description**: Store platform integrations in existing config maps by using URI-like strings as paths.
- **Pros**: Smaller first patch because many existing functions already accept strings.
- **Cons**: Existing path normalization would convert or compare these identifiers as filesystem paths.
- **Why rejected**: It creates hidden coupling between platform identity and local file behavior.

### Alternative 2: Create Fake Filesystem Paths

- **Description**: Represent each platform as a fake path under an AutoManager directory.
- **Pros**: Avoids schema changes in the short term.
- **Cons**: Misrepresents platform integrations as files and risks confusing UI, deletion, rename, and default-model flows.
- **Why rejected**: It breaks the product requirement that platform integrations be distinct but colocated with local models.

## Consequences

### Positive

- Separates file-backed local models from platform-backed runtime integrations.
- Avoids path-normalization bugs for platform IDs.
- Gives the proxy and UI a clear way to label local versus platform backends.

### Negative

- Some existing routes and frontend code must learn `backend_id` alongside `model_path`.
- Smart proxy settings need a compatibility migration from path-only primary selection to backend-aware selection.

### Risks

- Partial migration could leave UI code comparing `model_path` against `backend_id`. Mitigation: add unit and contract tests for model cards, status, proxy eligibility, and primary backend selection.

## Implementation Notes

Add helper functions that resolve a backend key from either `{backend_id, backend_type}` or legacy `{model_path}` payloads. New platform-aware endpoints should accept `backend_id`; existing local model endpoints should keep accepting `model_path`.

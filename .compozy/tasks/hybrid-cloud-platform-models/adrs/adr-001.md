# ADR-001: Unified Catalog MVP for Hybrid Platform Models

## Status

Accepted

## Date

2026-07-09

## Context

AutoManager already presents local `.gguf` models as cards, lets the local operator start them, exposes running instances through the local `/v1` API, and includes a smart proxy for routing among eligible local backends. The requested product direction is to incorporate cloud subscription tools from CLIProxyAPI, specifically Codex, Claude Code, and Google Antigravity, without requiring manual configuration inside AutoManager.

The primary MVP user is the local operator who runs AutoManager on a personal or server machine. This user expects the panel to show what is available, activate a detected integration, and see it become available through AutoManager's API. Cloud integrations should not be hidden when unavailable; they should appear disabled with a simple reason.

## Decision

The MVP will use a Unified Catalog approach. AutoManager will display Codex, Claude Code, and Google Antigravity as first-class cards alongside local models when their applications are detected. A detected integration may appear even before credential validation succeeds. If it cannot be used at runtime, the card will show a disabled or not-ready state with a clear reason. When the operator starts an available integration from the UI, AutoManager will expose it as an available model through its own `/v1` model surface. The smart proxy will consider cloud integrations only when the operator marks them as eligible.

## Alternatives Considered

### Alternative 1: Proxy-First Hybrid Gateway

- **Description**: Prioritize the `/v1` API and smart proxy behavior, treating cloud and local backends primarily as routable API capacity.
- **Pros**: Strong fit for automation clients, external consumers, fallback, and availability routing.
- **Cons**: Less aligned with the selected local-operator persona; increases MVP scope before the UI experience is proven.
- **Why rejected**: The chosen MVP success metric is UI activation followed by visibility in `/v1/models`, not advanced routing behavior.

### Alternative 2: Cloud Control Center

- **Description**: Build a richer cloud-provider management area with provider health, credentials, quota, troubleshooting, and detailed provider status.
- **Pros**: More comprehensive operating experience and better long-term diagnostics.
- **Cons**: Larger scope, more product surface, and a higher chance of delaying the core hybrid catalog value.
- **Why rejected**: The MVP should preserve AutoManager's existing local-model workflow and add cloud options without creating a separate management product.

## Consequences

### Positive

- Preserves AutoManager's current operator-centered workflow.
- Makes cloud integrations discoverable without requiring manual configuration.
- Gives the operator explicit control over whether cloud backends participate in smart proxy routing.
- Creates a narrow MVP success criterion: start a detected integration and see it in `/v1/models`.

### Negative

- Runtime readiness may differ from detection readiness, so cards need clear status language.
- Advanced quota, account pool, and failover behavior remain deferred.
- Some API-first users may need later phases before the gateway fully meets their needs.

### Risks

- Users may assume detected means fully authenticated. Mitigation: use explicit card states and simple reason text.
- Cloud subscriptions may behave differently by provider or plan. Mitigation: keep MVP provider states simple and defer provider-specific control details.
- Using cloud subscriptions through a local gateway may require careful user messaging. Mitigation: present detected integrations as user-owned local tools and avoid collecting separate credentials inside AutoManager.

## Implementation Notes

The PRD must remain product-focused. Technical design for detection, lifecycle, compatibility, provider adapters, and routing belongs in the follow-up TechSpec.
